CLI options

node dist/cli.js [directory] [options]

The directory defaults to the current working directory. Quote globs so the scanner receives the pattern directly.

--project config
Select a config relative to the scan root and follow its transitive project references. Repeat to select multiple configs.
--exclude glob
Omit matching files from the inventory, including imported files. Repeat to combine patterns.
--test glob, --tooling glob, --production glob
Override scope by slash-separated path relative to the root. Each is repeatable. Test takes precedence over tooling, then production, then the default path conventions.
--symbol name-or-id
Query one declaration by exact unique name or snapshot ID. Supports summary and JSON.
--changed-since revision
Compare a local Git revision directly with the tracked working tree under the scan root, including staged and unstaged changes. Untracked files enter the diff once staged. The summary groups current references by caller or test file and shows module exports, including re-exports. Changed lines select overlapping declarations, including an enclosing declaration when the line also contains its own code. Reads include callback arguments. Test references identify source sites and do not establish runtime coverage. Removed lines use base coordinates. Deleted files and the old side of renames have no current declaration to query. Use this option on its own with summary output.
--package-entries
Trace module initialization from the root package's exports (or main) and bin targets. All runtime conditions and array alternatives contribute roots. Type-only branches, declaration files and JSON targets are skipped. Combine with --entry for framework or implicit roots. For compiled packages select the emitting --project so the compiler can map outputs to analyzed inputs. Subpath patterns such as "./features/*": "./dist/*.js" expand against analyzed files and their predicted JavaScript outputs. An exact subpath or a more specific pattern takes precedence, including private paths blocked with null. If a target pattern has no matching source or predicted output, select its source explicitly with --entry. External invocations of exported functions are outside this trace.
--entry-symbol name-or-id
Assume a function, method or constructor is invoked and trace calls from its body. For example, select GET when reviewing a route handler. A repeated name requires the snapshot ID shown in the ambiguity message. Repeat the option for multiple invocations. Add file entries to include module initialization. The library accepts reachability(inventory, [], { entrySymbols: ['GET'] }). The report records these assumptions as snapshot IDs in the optional entrySymbols array.
--entry-glob glob
Trace analyzed files matching a quoted, root-relative pattern such as 'src/routes/**/+page.ts'. Repeat the option or combine it with --entry and --package-entries. Each pattern must match an analyzed file. Library callers can pass reachability(inventory, [], { entryGlobs: ['src/routes/**/+page.ts'] }).
--entry source-file
Trace paths from an analyzed file relative to the scan root. Repeat for multiple entries. Use a separate query for --symbol.
--format summary|json|markdown
Choose terminal text (default), machine-readable JSON, or a Markdown report.
--output new-file
Write the result to a new file. An existing path produces an error.
--strict
Signal a partial scan after writing its report. See exit codes.
-h, --help
Print usage and exit.

Exit codes

0 · Success
The CLI printed help or produced the requested report. Without --strict, both complete and partial scans succeed. Check the JSON completeness field when the distinction matters.
1 · Command failed
An invalid option, failed query, or read or write error sends an explanation to stderr. Stop before consuming output. In particular, an existing --output file may be from an earlier run.
2 · Strict scan produced a partial report
Read the report from stdout or the new file named by --output. Inspect its diagnostics before using the results. A complete scan with --strict exits with 0.

Project selection

node dist/cli.js . --project tsconfig.build.json --exclude '**/generated/**' --test 'qa/**'

The scanner discovers TS, TSX, JS, JSX, MTS, CTS, MJS, and CJS files. By default it reads the root tsconfig.json, falling back to jsconfig.json, then to discovered source. Configs supply compiler options, root file selection, and path aliases. A solution config with an empty files list can select a reference graph. Imported source may enter a program even when excluded from the config’s root list.

Each file is counted once. If multiple configs explicitly include a file, the one with the shortest relative path to it owns the file. Config path order breaks ties. An imported file outside every root list belongs to the first importing project in config path order. The file record identifies its owner. Scan projects separately when a shared file has different alias resolutions.

Discovery skips symlinks, declaration files as inventory inputs, and the contents of node_modules, .git, dist, build, coverage, .next, .nuxt, and .output. The compiler can still read declarations for resolution. Discovered files excluded from the inventory carry a reason.

When a JavaScript file imports an explicit relative path such as ./codec.js, the scanner traces references into that implementation if it is in scope, even when it has an adjacent declaration file. TypeScript diagnostics still use the project's declared types.

Paths containing test, tests, __tests__, __mocks__, or fixtures as directory names, and .test or .spec files, receive test scope. The scanner labels scripts, tools, and *.config.* as tooling. Other files default to production. The equivalent library options are scan(root, { projects, exclude, scopes }), where each scope maps to an array of globs.

Counts and findings

usages() groups resolved occurrences into calls, construction, reads, type references, imports, re-exports, and JSX. An import or re-export alias contributes one reference even if no code uses the binding. A call inside a loop contributes one direct call site. An explicit constructor and its class each receive a relationship for the same construction site. Distinct callers count the containing declarations of call and construction sites, grouping top-level sites by module.

findings() separates local declarations without meaningful usage from exports without local usage. Imports and re-exports alone do not count as meaningful usage. Export visibility includes exports anywhere in the analyzed source. Review the package’s entry points to determine which exports it exposes.

JSON snapshot

schemaVersion, analyzer, snapshotId
Record the format version, analyzer and compiler versions, and report identity. A symbol ID is tied to its declaration location within the snapshot.
config, files
Record selected configs, project paths and config input hashes, plus file hashes, status, exclusion reasons and project ownership. Resolution-only inputs such as installed declarations and package metadata fall outside the fingerprint.
symbols, references, modules, exports
Describe declarations and their locations, resolved occurrences, module edges, and exported names. Source bodies and the absolute root path are omitted. Locations use one-based lines and columns and zero-based UTF-16 offsets with an exclusive end.
completeness, diagnostics, limitations
A partial result includes diagnostics. A complete result means the supported analysis emitted none. Read the limits when interpreting either result.

A symbol query returns a usage object with its symbol, counts, and references alongside schema version, snapshot ID, diagnostics, and completeness. An entry query returns the selected entries, reached nodes with shortest-path predecessors, and declarations labeled reachable or no-known-path, along with snapshot ID, completeness, diagnostics, and limitations.

Consuming the 0.x API

The package root exports scan, usages, findings, reachability, packageEntries and entryPath. scan reads a directory synchronously. The other queries operate on its inventory or reachability report, except packageEntries(directory, inventory), which also reads the matching manifest and build configuration. Pass its result to reachability. entryPath(report, symbolId) returns the ordered nodes of one shortest path, including the selected file or invocation root and target, or null for an unreached ID. Select the ID with usages. Each non-root node carries the edge kind and source location. summary, usageText and markdown render display text.

Saved reports and 0.x upgrades

Use --format json for scripts. The packaged JSON Schema lists the required properties, types, allowed values and nullable fields for each report. Summary, Markdown, diagnostic messages and limitation text are for display. --changed-since produces a text summary.

Full inventory
Require schemaVersion === 1 for the layout above. Save the full inventory to run new usages or reachability queries later. Use analyzer.version and analyzer.compilerVersion to identify the producer.
Symbol query
Require schemaVersion === 1 and read usage.symbol, usage.references and usage.counts. The CLI puts snapshot-wide diagnostics alongside usage.
Entry query
In 0.3.0 this report has no schemaVersion. Validate it against the schema’s entryReport definition. File roots appear in entries. The optional entrySymbols lists explicitly invoked declarations. Use reached to reconstruct paths and declarations to look up reachability status.

All three shapes carry snapshotId, completeness and diagnostics. Keep the matching inventory or its producer metadata with a saved query. Treat IDs as opaque and join records only within the same snapshot. A fresh scan with an improved resolver can produce different IDs, counts, paths or diagnostics for the same source.

Within schema version 1, readers can rely on required fields and their documented meanings. Producers may add optional fields and diagnostic codes. Ignore unfamiliar properties, handle unfamiliar codes, and allow optional fields such as files[].project to be absent. A required field with a nullable type, such as references[].callerId, is present even when its value is null.

During 0.x, a change that invalidates existing reports or breaks a reader following these rules belongs in a new minor release with migration instructions. An incompatible JSON shape also needs a new schema version, including an explicit version on a replacement for the unversioned entry report. A change to the documented exit codes is likewise a breaking CLI change. Before moving to another minor release, validate a saved report with the target schema and replay a representative query. For an unsupported version, retain the original report and use its generating release until you migrate.

TS-prefixed codes are compiler diagnostics. unresolved-module and dynamic-module identify missing module edges. unresolved-call, mutable-binding and accessor-dispatch identify uncertainty about invocation targets. Inspect the diagnostic location alongside the usage or path. Scope is snapshot-wide, so a partial scan can still contain individually verifiable calls. The inventory summary groups diagnostics by code.

Analysis limits

Scanning reads source and configuration without executing modules, tests, or configuration scripts. Parse errors, unresolved imports or calls, computed module paths, accessors, and mutable function bindings can produce diagnostics. Implicit getter and setter dispatch, reflection, and framework conventions can hide usages. The adapter uses Microsoft’s TypeScript 6 compatibility package with compiler engine 6.0.3.

Reachability follows direct calls, construction, static imports and re-exports, and literal dynamic imports or requires in their containing scope. It skips explicit type-only module edges. Emitted JavaScript may omit other imports too. Conditional branches can contribute paths. Recursion within an isolated group creates references without making it reachable from an entry. Runtime behavior, test coverage, and safe removal require additional evidence.
